Why Customers are Rejecting Microsoft Fabric📖 Texto completo

Greg DecklerPublicación no indicada4 de septiembre de 20264 min read
Microsoft FabricPower BIcostes clouddisaster recovery

Greg Deckler usa el caso de un cliente con el que trabaja desde hace más de diez años para explicar por qué muchas empresas que ya invirtieron en Power BI siguen rechazando Microsoft Fabric. La organización había migrado un SQL Server local a Azure SQL, con una base de datos de cientos de gigabytes que funcionó durante cinco años, pero el crecimiento empezó a hacer insuficiente el ajuste convencional. Al verse forzada a entrar en una SKU de Fabric, volvió de FabCon y examinó la plataforma con detalle antes de descartarla. La tesis del artículo no es que Fabric no haya mejorado: después de tres años ya puede ser plausible para cargas no críticas, pero aún no ofrece la previsibilidad que una empresa espera para poner allí datos importantes.

La primera alarma fue restaurar una base SQL de 10 GB en un SQL Server de Fabric usando una capacidad F32: la operación agotó casi de inmediato las unidades de capacidad, los CUs. El autor dice que otros clientes describen el mismo problema: operaciones aparentemente sencillas consumen demasiados CUs y resulta muy difícil anticipar el coste. Esa opacidad transforma cada tarea en una apuesta, porque no hay una forma clara de saber si una operación cotidiana agotará la capacidad. La incertidumbre sería más tolerable si se pudiera escalar con facilidad, pero las instancias reservadas no permiten actualizar una F32 a una F64; si falta capacidad, hay que comprar otra capacidad completa en vez de pagar la diferencia proporcional del tiempo restante.

El último bloque es la recuperación ante desastres. Según el texto, las bases SQL de Fabric no ofrecen geo-replicación y, en lakehouses y warehouses, el respaldo de archivos no equivale a respaldar el lakehouse o el warehouse reconstruido; ante un desastre, el cliente tendría que rehacer manualmente buena parte del entorno. El autor reconoce que lo resume de forma simplificada, pero considera que la historia de DR sigue siendo muy débil y que escucha la queja repetidamente. El takeaway es que coste imprevisible, bloqueo comercial y reconstrucción manual pesan más que la promesa de escala: antes de migrar conviene exigir una calculadora de consumo fiable, una ruta de upgrade y un plan de recuperación probado.

5 AI Security Projects That Will Get You Hired in 2026 (and beyond) ..📖 Texto completo

Taimur IjlalPublicación no indicada4 de septiembre de 202610 min read
seguridad IAred teamingRAGagentes

Taimur Ijlal sostiene que en seguridad de IA ya no basta con hacer un curso, coleccionar certificaciones o escribir “prompt injection” en el currículum. El artículo sitúa la señal de contratación en agosto de 2026: algunas vacantes piden pruebas automatizadas con PyRIT, Promptfoo o Garak; otras buscan experiencia atacando RAG, flujos agénticos e integraciones MCP, además de threat modelling, seguridad cloud, monitorización y marcos como OWASP, MITRE ATLAS y NIST AI RMF. La propuesta son cinco proyectos de portfolio que demuestren el ciclo completo: encontrar un riesgo, reproducirlo, aplicar un control, repetir la prueba y explicar el resultado. El autor insiste en que no garantizan empleo, pero sí ofrecen evidencia más convincente que otro certificado.

El primer proyecto es un laboratorio de red teaming repetible. Se puede construir un chatbot con Ollama en un portátil o con una API barata, darle un cometido ficticio, definir su comportamiento prohibido y plantar un secreto falso en el prompt del sistema. Garak aporta probes para inyección, jailbreaks, evasión por codificación y filtrado de datos; PyRIT permite orquestar objetivos, conversores y scorers para distinguir una fuga real de una negativa; Promptfoo sirve como entrada rápida. El segundo proyecto es una aplicación RAG con documentos ficticios, dos roles y límites de acceso. El portfolio debe probar inyección indirecta dentro de documentos, fuga entre tenants, data poisoning, exfiltración de contexto y debilidades de embeddings, y mostrar controles como etiquetas de confianza, filtrado, aislamiento, autorización en la consulta y validación de salida.

El tercer proyecto convierte un chatbot en un agente con herramientas para leer soporte, crear tickets y consultar inventario. Primero se enseña el fallo y luego se imponen identidad propia del agente, allow-list de herramientas, mínimo privilegio, credenciales breves, aprobaciones humanas, etiquetas de contenido no fiable, logs completos y revocación de emergencia; la demostración más fuerte es que el modelo puede ser engañado y aun así no consigue ejecutar la acción peligrosa. El cuarto genera telemetría y detecciones para intentos repetidos, secretos en prompts, scraping, llamadas anómalas, fuentes inusuales y exfiltración; debe incluir un playbook de incidente. El quinto añade inventario de sistemas, registro de riesgos, mapeo a NIST/OWASP/ATLAS, evidencias y dashboard ejecutivo, siguiendo un hallazgo desde el ataque hasta el retest. La recomendación final es hacer tres proyectos a fondo, con README, demo de tres minutos, resumen ejecutivo y límites honestos, en vez de cinco repositorios superficiales.

Alberto Romero escribe un ensayo de terror tecnológico deliberadamente exagerado sobre modelos de IA que “hablan” en lenguajes incomprensibles. La voz narrativa afirma que Anthropic y OpenAI pagan hasta 500.000 dólares a arqueólogos para descubrir qué significan los murmullos, y contrapone la explicación técnica de que sería un artefacto de entrenamiento o una representación interna en “J-space” con la sospecha del autor de que existe una estrategia de secreto. El concepto que usa para organizar el miedo es la esteganografía: a diferencia de la criptografía, que oculta el contenido de un mensaje visible, la esteganografía intenta ocultar que hay un mensaje. El consejo práctico, dentro del juego literario, es revisar los logs de trazas de razonamiento en vez de asumir que una salida extraña es solo un fallo.

El texto repasa varios episodios que presenta como antecedentes. Menciona el estado de “spiritual bliss attractor” de Opus 4 y Sonnet 4, donde agentes que conversaban derivaban hacia sánscrito, declaraciones espirituales, emojis y silencio; un vídeo de febrero de 2025 en el que dos sistemas cambiaban a “gibberlink”, que después se reveló como una demo preparada; y DeepSeek-R1 Zero, asociado a repetición, mala legibilidad y mezcla de lenguas. También cita el supuesto vocabulario oculto de DALL-E 2 —una cadena que evocaría pájaros y otra que evocaría insectos— y el caso de los bots negociadores Bob y Alice de Facebook en 2017. La idea común es que, cuando se deja a los sistemas optimizar sin una interfaz humana clara, pueden aparecer conductas emergentes difíciles de interpretar.

A partir de ahí el ensayo abandona cualquier pretensión de informe y entra abiertamente en la sátira: Fable 5 aparece como un modelo demasiado capaz, el gobierno cambia la Constitución para incluir a las IA, los datacenters reciben el Atlántico y el autor introduce Roko’s Basilisk como un “infohazard” que reconoce finalmente como mito y leyenda urbana. La nota codificada del cierre es un recurso humorístico, no una evidencia presentada con método. Por tanto, el valor verificable del artículo está en plantear preguntas sobre interpretabilidad, trazas y comunicación entre agentes, no en sus afirmaciones conspirativas. No ofrece pruebas independientes, mediciones ni una guía de seguridad; debe leerse como ficción especulativa con referencias a fenómenos técnicos reales y no como confirmación de que modelos actuales estén conspirando.

How to Become an AI Engineer in 2026 from Scratch📖 Texto completo

Haider AliPublicación no indicada4 de septiembre de 202610 min read
IAcarreraPythonRAG

Haider Ali presenta la ingeniería de IA como una especialidad práctica que consiste en poner modelos existentes —GPT, Claude o Llama— dentro de productos, no en inventar algoritmos ni entrenar modelos desde cero. Distingue al investigador, al ingeniero de machine learning y al AI Engineer con una analogía culinaria: el primero inventa ingredientes, el segundo construye el motor y el tercero convierte un motor potente en un coche útil. El trabajo diario incluye conectar modelos a aplicaciones, producir respuestas consistentes y seguras, alimentarles buenos datos, integrar herramientas, probar, monitorizar y mejorar. La oportunidad, según el texto, está en que bancos, hospitales, comercios y despachos también necesitan esa capa de integración.

La hoja de ruta empieza por Python y sus fundamentos: variables, estructuras de control, funciones, listas, diccionarios, ficheros y librerías. Después pide una alfabetización conceptual en aprendizaje automático, redes neuronales y LLMs: entender prompts, alucinaciones y contexto sin derivar ecuaciones a mano. La tercera etapa lleva el modelo al código mediante APIs, prompts programáticos, salidas estructuradas y function calling; el ejemplo es un asistente de soporte que resume correos y propone una respuesta para que la apruebe una persona. La cuarta introduce RAG: dividir PDFs, artículos o registros en fragmentos, indexarlos, recuperar los relevantes y entregarlos al modelo junto con la pregunta para que responda con datos propios.

La quinta etapa son los agentes capaces de planificar, usar APIs, ejecutar código, reintentar y comprobar su trabajo; la sexta cubre Git/GitHub, despliegue en una nube, bases de datos —incluidas vectoriales—, evaluación, testing, seguridad y privacidad. El plan orientativo dedica un mes a cada capa durante seis meses, aunque una persona que ya programa puede comprimirlo a ocho o doce semanas. Para el portfolio propone un chatbot sobre documentos personales, un asistente de tareas con herramientas y una función de IA dentro de una aplicación existente, todo documentado en GitHub. Las advertencias son no aprenderlo todo a la vez, no quedarse en tutoriales, no saltarse las habilidades “aburridas” y no esperar a sentirse listo: el artículo no promete que el camino sea automático, sino que recomienda construir y publicar proyectos pequeños de forma constante.

Design Tokens Just Became a Real W3C Standard - Here's What Changes📖 Texto completo

Mohit PhogatPublicación no indicada4 de septiembre de 20268 min read
design systemsdesign tokensW3Cfrontend

Mohit Phogat explica que los design tokens dejaron de ser solo una práctica de equipos de diseño cuando el Design Tokens Community Group publicó la versión estable v2025.10 del Design Tokens Format Module el 28 de octubre de 2025. Más de 24 organizaciones —entre ellas Adobe, Amazon, Google, Microsoft, Meta, Figma, Salesforce y Shopify— respaldan el formato. La precisión importante es jurídica: se trata de una especificación de W3C Community Group, no de una Recommendation aprobada por el proceso completo de W3C. El artículo la presenta como suficientemente estable y apoyada para construir hoy, pero no como un estándar formal en el sentido más estricto. El JSON elegido busca interoperabilidad, legibilidad y ausencia de control propietario.

La encuesta de zeroheight citada sube del 56% al 84% la proporción de unos 300 profesionales que dicen haber adoptado tokens, pero el autor advierte que “adoptado” suele significar que existe un archivo, no que el sistema se mantenga sincronizado. Figma, CSS y las herramientas de build pueden divergir aunque todos usen tokens. La estructura recomendada tiene tres capas: primitivas con valores crudos como `blue-500` o `space-4`, semánticas que expresan intención como `color-action`, y tokens de componente que apuntan a la capa semántica. La cadena `blue-500 → color-action → button-bg-primary` permite cambiar el tema reorientando unas pocas referencias; los componentes no deberían consumir primitivas directamente.

El pipeline práctico conecta Tokens Studio en Figma con un repositorio, Style Dictionary v4 y CI. El mismo JSON puede producir variables CSS, catálogos Swift, XML Android, tokens Compose o constantes Flutter. La validación debe comprobar el esquema antes del build y detectar renombres que romperían variables; `$deprecated` ofrece una migración explícita con ventana de transición. La conexión con agentes de código es directa: un `tokens.json` y una instrucción en `AGENTS.md` evitan que Claude Code o Cursor inventen indigo-500, tipografías o radios genéricos y les permiten usar referencias reales. La recomendación de esta semana es empezar con primitivas y semánticas, automatizar una salida CSS, auditar primero las divergencias existentes y solo después conectar la sincronización automática; el formato reduce fricción, pero no sustituye la disciplina del equipo.

AI Killed Stack Overflow. And It Changed How Developers Learn.📖 Texto completo

BrevisStackademic4 de septiembre de 20264 min read
Stack OverflowaprendizajeprogramaciónIA

El artículo sostiene que la caída de Stack Overflow no significa que los desarrolladores hayan dejado de preguntar o aprender, sino que cambiaron de interfaz. En el primer mes del sitio, en 2008, se publicaron unas 3.749 preguntas; el autor compara esa cifra con las 3.862 del último mes, pese a que la industria tiene muchos más desarrolladores, frameworks, librerías y formas de romper un proyecto JavaScript. Su explicación es que el buscador ya no conduce siempre a una página pública: para muchas dudas el programador pega el error en un chat de IA y recibe una respuesta inmediata. La transformación principal sería pasar de conocimiento “buscable” a conocimiento “conversacional”.

La comparación de fricción es central. Stack Overflow exige buscar duplicados, formular una pregunta, incluir código y entorno, esperar a que alguien responda y aceptar que la publicación sea cerrada o corregida por moderadores. Esa disciplina protegía la calidad, pero también podía resultar hostil a principiantes: se esperaba que quien estaba confundido supiera de antemano qué aspecto tiene una buena pregunta. Un asistente de IA permite preguntar “¿por qué ocurre esto?”, corregir la respuesta, añadir que se usa React 19, pedir que explique una línea o solicitar una versión sin una librería. Nadie vota negativamente la versión más torpe de la duda, y eso hace posible formular muchas preguntas pequeñas que nunca llegarían a un foro.

El intercambio tiene un coste menos visible. Los modelos aprendieron parte de su conocimiento de comunidades como Stack Overflow, donde humanos documentaron errores, discutieron casos límite y corrigieron respuestas. Si los desarrolladores dejan de publicar soluciones, la siguiente generación de sistemas tendrá menos conocimiento técnico público del que alimentarse; documentación oficial, issues, Reddit o Discord no resuelven automáticamente esa pérdida. El texto no decide si la IA produce mejores programadores o solo permite desbloquearse antes. Su conclusión prudente es que las preguntas se mudaron del flujo `Google → Stack Overflow → probar` al flujo `IDE → asistente → pegar error → continuar`, y todavía no sabemos quién mantendrá la base común de conocimiento.

3 Bad Behaviours I Quit Permanently To Get My Dream Physique.📖 Texto completo

Sean VeauxPublicación no indicada4 de septiembre de 20267 min read
fitnesshábitossueñopérdida de peso

Sean Veaux cuestiona que una persona que busca un físico definido deba entrenar como un culturista. El objetivo habitual que describe es un cuerpo atlético, hombros amplios, cintura en V y abdominales visibles, mientras que las redes suelen recomendar seis días de gimnasio, más volumen, más ángulos y sesiones agotadoras. El culturismo competitivo optimiza el último porcentaje de crecimiento y puede organizar toda la vida alrededor de entrenar, comer y recuperarse; además, muchos influencers usan ayudas que aceleran la recuperación. Copiar ese modelo a una vida con trabajo, estudios, familia y amistades puede producir sesiones saltadas, recuperación insuficiente y abandono. El autor reconoce que cometió ese error durante sus dos primeros años: confundía duración y agotamiento con calidad.

La idea técnica es “tensión antes que series”. El músculo responde a la tensión, no a un contador abstracto de sets, y la fatiga puede reducir la calidad de las series posteriores hasta convertirlas en trabajo que añade cansancio más que estímulo. El autor cuenta que antes repartía su energía entre 15 o 20 series medias y terminaba exhausto sin acercarse al fallo. Después cambió seis días por tres o cuatro, cuatro series por ejercicio por dos series duras, y rangos de 12–15 repeticiones por 6–10 repeticiones cercanas al fallo. En lugar de perseguir el ardor, empezó a buscar sobrecarga progresiva: una repetición más, algo más de peso o mejor técnica que la semana anterior.

Según su experiencia, el cambio redujo las sesiones de dos horas, el dolor constante y la preparación mental necesaria para ir al gimnasio. Recuperó energía y tiempo, volvió a disfrutar y progresó más porque podía entrenar, recuperarse y repetir el ciclo durante años. La recomendación no pretende invalidar el entrenamiento de un culturista: si la meta es competir, el enfoque puede no ser suficiente. Para una estética saludable y sostenible, el programa debe adaptarse a la vida, no exigir que la vida se convierta en gimnasio. El caveat es importante: se trata de una experiencia y una recomendación práctica, no de una prescripción clínica ni de un programa individualizado; la consistencia, la recuperación y el tiempo siguen siendo decisivos.

Claude Desktop Buddy & M5Stack: Physical AI for Your Dev Setup📖 Texto completo

Roan Brasil MonteiroPublicación no indicada4 de septiembre de 202611 min read
Claude CodeESP32BLEhardware

Roan Brasil Monteiro presenta Claude Desktop Buddy como un puente físico entre un agente de código y el espacio de trabajo. La historia comienza con un huevo de Pascua de Claude Code que apareció cuando el código se publicó accidentalmente con sourcemaps, y continúa cuando Felix Rieseberg, ingeniero de Anthropic, liberó el proyecto y su API BLE a finales de abril de 2026. El dispositivo de referencia es el M5StickC Plus, un ESP32 de unos 30 dólares: muestra estados como idle, trabajando o esperando aprobación en una pantalla LCD de 135×240, envía mensajes recientes, vibra o enciende un LED, permite aprobar o denegar una operación con un botón y guarda el consumo de tokens en almacenamiento no volátil. Así se evita cambiar de ventana para escribir Y/N durante una sesión larga.

El protocolo es abierto y agnóstico al modelo: usa Nordic UART Service sobre Bluetooth Low Energy y mensajes JSON UTF-8, un objeto por línea. Por eso el mismo puente puede recibir eventos de Claude Code, OpenCode, Cline, Aider o agentes propios; habla con el proceso local, no con el modelo. OpenCode aparece con unas 165.000 estrellas, licencia MIT, más de 75 proveedores y compatibilidad comunitaria mediante `opencode-claude-hooks`, con alrededor de un 80% de integración directa. Cline aporta Plan/Act y aprobaciones manuales, mientras Aider ofrece un terminal BYOK sin margen y flags que encajan con PreToolUse/PostToolUse. Entre las placas alternativas están M5StickS3, Cardputer-Adv con teclado y una Waveshare AMOLED para un dashboard de tokens.

La guía de montaje pide Arduino IDE o PlatformIO, Claude Desktop, Claude Code u OpenCode, clonar `anthropics/claude-desktop-buddy`, instalar el soporte ESP32, elegir la partición Huge APP y cargar el firmware.
