Frontend Architecture Mistakes That Kill Scalability📖 Texto completo

Rupal Singhal (Full-Stack Developer)Medium26 de septiembre de 202610 min read
frontendarquitecturaReactrendimiento

El artículo define la escalabilidad frontend como la capacidad de hacer cambios previsibles: que varios desarrolladores puedan añadir funcionalidades sin pisarse, que una modificación no rompa pantallas ajenas y que alguien nuevo entienda el código sin descifrarlo durante semanas. La tesis no es que React sea el problema, sino que una arquitectura basada únicamente en componentes termina mezclando presentación, negocio, datos e infraestructura. El autor propone pensar en límites sucesivos —UI, features, dominio, acceso a datos e infraestructura— y agrupar cada capacidad, como checkout, con sus componentes, hooks, servicios, tipos y utilidades. Así se puede localizar o eliminar una feature sin rastrear treinta carpetas globales.

Los errores se repiten en el “God Component”, que empieza como un Dashboard de 150 líneas y acaba gestionando usuarios, analítica, filtros, permisos, modales, paginación y formularios; en meter todo en Redux; en duplicar estado derivado; y en abstraer componentes genéricos con tantas variantes que dejan de ser comprensibles. El texto distingue estado local de UI, estado de feature, estado compartido y server state, recomienda derivar `filteredProducts` en lugar de sincronizarlo y pide una dirección explícita de dependencias. También separa reglas de negocio, crea una frontera `hook → service → API client`, mapea la respuesta de API a un modelo de dominio y usa TypeScript como límite arquitectónico.

La segunda mitad conecta arquitectura y rendimiento: code splitting para no enviar editores, gráficos o rutas raras al bundle inicial, estrategia de caché definida desde el diseño, presupuestos de JavaScript, LCP, INP, CLS, imágenes y latencia, y procesamiento fuera de componentes. La prueba final son cinco preguntas: si la feature se puede borrar limpiamente, si se entiende de forma aislada, si tiene una única fuente de verdad, si cambia sin afectar a otras y qué ocurrirá cuando el producto sea diez veces mayor. El autor no recomienda sobre-ingeniería ni microservicios por reflejo: la arquitectura buena hace más barato el cambio, no predice el futuro.

What Component Specs Leave Behind📖 Texto completo

Nathan CurtisMedium26 de septiembre de 202610 min read
Figmadesign systemsspec-driventesting

Nathan Curtis usa el teletransporte de Spock como metáfora para explicar que un componente puede conservar color, forma y variantes visibles y aun así perder la intención que lo hacía ser realmente el mismo componente. En un flujo de UI guiado por especificaciones, el recorrido Figma → spec puede emitir un código hexadecimal cuando debía conservar un token, perder un `maxWidth`, omitir la interacción entre `selected` y `hover`, o confundir una propiedad BOOLEAN con un SLOT. El problema es que una revisión visual no siempre revela esas pérdidas: el contrato puede parecer limpio precisamente porque nunca transportó la parte difícil.

La propuesta es probar el contrato en sentido inverso. El autor construye un comando `render` determinista que convierte una spec en un componente de Figma y lo ejecuta en un bucle: generar una spec base, renderizar un componente de prueba, volver a generar la spec, comparar ambas, agrupar las diferencias y borrar el componente de prueba. Un puente conecta Figma con el chat del modelo y con datos cacheados de variables, iconos y assets. El informe valida recuentos y formas de variantes, distingue funcionalidades aún no implementadas de regresiones y convierte los temas encontrados en issues priorizados. Repetir el proceso sobre toda una biblioteca redujo las diferencias hasta un residuo inspeccionable y llevó el render a la paridad con generate.

El resultado no es perseguir un diff vacío a cualquier precio, sino nombrar qué se reafirma, qué es un defecto y qué el contrato no puede, no quiere o todavía no puede llevar. Las rondas descubrieron que el orden alfabético destruye orden autoral, que los booleanos deben conservarse como booleanos y que visibilidad no equivale a existencia; también sacaron a la luz un `clipContent` mal definido, restricciones de slots silenciosas y la necesidad de una gramática segura para conservar nombres de Figma. Quedan límites explícitos: orden personalizado de props, ciertas variables con aspect ratio bloqueado, Grid y motion. El takeaway es aplicar round trips incluso sin un render determinista, para separar intención transportada, pérdida y falta de profundidad.

RAG is a knowledge interpreter. Time for a compiler - Compile-Time RAG📖 Texto completo

Jaroslaw WasowskiMedium26 de septiembre de 202613 min read
RAGagentesLLMcontexto

La tesis de Compile-Time RAG es mover el trabajo interpretativo fuera de la ruta de cada petición. En el RAG clásico, cada consulta vuelve a trocear o consultar conocimiento, re-embebe la pregunta, busca fragmentos y mete texto crudo en el contexto. Para un chatbot de un solo turno ese coste ocurre una vez; para un agente que ejecuta decenas de pasos, se repite como un “impuesto” sobre cada iteración. El autor cuenta el caso de un agente antifraude que funcionaba con 50 usuarios, triplicó la factura alrededor de 500 y dejó de ser económicamente viable cerca de 700 porque cada bucle redescubría el mismo contexto.

La alternativa compila de antemano un corpus estable en un artefacto orientado a una tarea: una tabla tipada, un perfil de entidades, una gráfica de dependencias o un documento estructurado. Así las relaciones entre hechos quedan resueltas antes de que el agente pregunte, en vez de obligarlo a unir fragmentos que ni siquiera son adyacentes. El pipeline separa compile, index y serve: un Context Compiler itera contra un conjunto de evaluación; los artefactos terminados van a un índice híbrido; y el agente recibe una consulta declarativa con resultados tipados y citas de campo, en el ejemplo mediante KnowQL. La propuesta se compara con vistas materializadas de bases de datos y con la idea de LLM Wiki de mantener conocimiento compilado.

El texto cita un benchmark interno de Pinecone sobre informes 10-K: unos 6.700 tokens por pregunta para el enfoque compilado frente a unos 49.000 para agentic RAG, pero recalca que es un resultado del propio proveedor sobre 150 preguntas. El supuesto ahorro de alrededor del 90% se compensa con el coste de compilación, y la tabla publicada de latencia da 22,7 frente a 37,9 segundos, no el “30x” promocional. WiCER encontró pérdidas catastróficas en el 53–60% de los casos sin verificación iterativa; con compilación iterativa recuperó cerca del 80% de la calidad, aunque no alcanzó el contexto completo. La recomendación es híbrida: compilar datos estables, recuperar en tiempo real lo dinámico, lo sujeto a permisos o lo impredecible, y programar recompilaciones para que los artefactos no envejezcan en silencio.

El texto aclara que una presentación “estilo McKinsey” no se define por fondo blanco, formas azul oscuro o una fuente concreta, sino por una disciplina de comunicación. La conclusión debe aparecer pronto, cada diapositiva necesita una tarea, la evidencia debe sostener la afirmación y la página debe poder entenderse con rapidez. El proceso comienza por la decisión que la presentación tiene que apoyar: se escribe una respuesta en una frase, se descompone en argumentos, se asigna evidencia y se lee la historia únicamente a través de los títulos antes de abrir PowerPoint.

Las ocho reglas convierten esa idea en un flujo operativo. Los títulos deben ser conclusiones accionables, no etiquetas; cada diapositiva debe responder a una sola pregunta; la forma visual debe coincidir con la relación de los datos —proceso, ciclo, jerarquía o conexión—; y los gráficos deben funcionar como evidencia, con una comparación relevante, colores contenidos y fuentes que indiquen organización, documento, fecha y página cuando sea posible. La jerarquía se crea primero con espacio, retícula, márgenes y alineación; el texto normal debe respetar como referencia el contraste 4,5:1 del W3C. El autor propone una familia pequeña de plantillas y tres revisiones separadas: historia, validación de números y diseño/exportación.

Tosea AI aparece como herramienta fuente-grounded para convertir PDFs, papers, informes financieros o estudios en PowerPoint editable. Permite proponer layouts y diagramas durante el esquema —comparación, Gantt, fishbone, SWOT, PEST, dashboards— y cambiarlos después del render si el contenido necesita otra estructura; intenta conservar cajas de texto, fuentes, iconos y formas editables. El prompt final pide audiencia, decisión, títulos-conclusión, evidencia, notas de fuente y aprobación del esquema antes de renderizar. El artículo usa “McKinsey” de forma descriptiva y declara no estar afiliado; tampoco ofrece precio, y advierte que las páginas complejas, fuentes corporativas y gráficos difíciles aún requieren revisión de exportación.

Ilya Zakharau parte de un problema de la ingeniería tradicional: tareas en Jira, documentación en Confluence, código en GitHub o GitLab y requisitos repartidos entre herramientas que pocas veces se mantienen alineadas. El enfoque docs-as-code mejora la situación para la documentación porque la pone bajo el mismo versionado que el código, pero no resuelve bien requisitos que cruzan módulos, repositorios o límites arquitectónicos. El propio autor reconoce que su idea de guardar requisitos en un repositorio separado sería peor que Confluence.

La llegada de los agentes cambia qué se considera fuente de verdad. La especificación puede quedar obsoleta antes incluso de terminar el desarrollo, mientras que el código pasa a ser desechable y regenerable a partir de un prompt. Spec-Driven Development intenta poner una especificación estructurada en el centro para que agentes de IA generen el código: la spec es determinista, pero el resultado ya no lo es. Por eso la ingeniería de requisitos se desplaza hacia prompt engineering y context engineering, con la exigencia de mantener la spec sincronizada con la implementación y, en proyectos grandes, integrarla con el código y la trazabilidad.

El autor conserva por ahora PRDs y BRDs para lectores humanos, pero plantea que podrían perder peso frente a artefactos que las máquinas consumen directamente; también califica como antipatrón usar un PRD empresarial sin más para generar código al estilo “vibecoding”. Nombra OpenSpec, MUSUBI, Spec-Kit y Superpowers como ejemplos de herramientas, aunque advierte que la lista podría ser completamente distinta en un año. La conclusión es deliberadamente ambivalente: su sueño de mover requisitos al código se acerca, pero SDD también puede vender una ilusión de control asociada a la reducción de costes y a una tecnología todavía no determinista.

How we improved image download sizes on Medium with just four characters📖 Texto completo

Scott BatsonMedium Engineering26 de septiembre de 20267 min read
webimágenesHTMLrendimiento

Scott Batson reconstruye la evolución de las imágenes web para explicar una mejora muy pequeña en el código. En los primeros años de las SPAs, los desarrolladores elegían con JavaScript una imagen para cada contexto porque HTML no tenía una forma declarativa de expresar la intención. `picture` permite decisiones prescriptivas —tema oscuro, tipo de archivo o imagen distinta para móvil—, mientras `srcset` describe varias resoluciones de una misma imagen y deja que el navegador elija usando información que el código de la aplicación no conoce bien, como conectividad, caché y contexto del sistema.

El atributo `sizes` ayuda al navegador a estimar el espacio que ocupará una imagen antes de que el layout esté pintado, pero sus reglas responsive pueden volverse difíciles de mantener. `loading="lazy"` evita descargar imágenes fuera del viewport inicial; hasta hace poco, faltaba una forma sencilla de combinar ese retraso con una selección adaptada al tamaño real. El artículo señala que el 24 de marzo de 2026 WebKit añadió soporte para `auto` en `sizes` de imágenes lazy. La instrucción es anteponer `auto`: el navegador decide, según layout, conectividad y dimensiones, la versión adecuada, y los navegadores que no entienden la regla la ignoran gracias al comportamiento existente del atributo.

La recomendación se presenta como una ganancia compatible y de bajo riesgo; WordPress ya habría actualizado sus imágenes lazy con ese patrón. En Medium, el autor observó que el fragmento de descarga de imágenes del feed era aproximadamente un 7% menor en una pantalla pequeña. La precisión requiere dos matices: el texto habla de cuatro caracteres, pero cuenta seis al incluir coma y espacio, y `picture` sigue siendo mejor cuando se necesitan imágenes art-directed, no solo resoluciones. La mejora no elimina la necesidad de definir `alt`, tamaños y fuentes razonables; simplemente permite que el navegador haga una decisión para la que posee más contexto que la aplicación.

Stop Shipping Individual MCP Servers. Start Shipping Agent Plugins📖 Texto completo

Andrii TkachukData Science Collective26 de septiembre de 202613 min read
MCPAgent Skillspluginsagentes

El artículo describe una secuencia de capas: MCP respondió a “¿a qué puede conectarse el agente?”, Agent Skills a “¿cómo debe hacer el trabajo?” y Agent Plugins empieza a empaquetar ambas cosas para distribuir una capacidad reutilizable. MCP estandariza el acceso a bases de datos, SaaS, archivos o APIs, pero un servidor que expone `search_documents` no explica cuándo usarlo, qué combinar, en qué orden ni qué significa un flujo correcto. Una Skill añade instrucciones, scripts y referencias para incorporar ese conocimiento operativo —por ejemplo, verificar fuentes, citar afirmaciones y no escribir en Salesforce durante una investigación.

El autor sitúa el lanzamiento público de Agent Plugins 1.0 el 6 de agosto de 2026: una especificación iniciada por Vercel junto con Amazon, Anysphere, Microsoft y OpenAI, con Google incorporándose después. El núcleo portable solo exige `plugin.json`, una carpeta `skills/` y `mcp.json`; los servidores proporcionan herramientas y datos y la Skill describe el procedimiento. El ejemplo de customer research podría instalarse desde un repositorio y permitir que un agente consulte conocimiento interno, Salesforce y documentos y produzca un informe, sin construir otra interfaz de chat u orquestador cuando el entorno de agentes ya existe. GitHub añadió soporte en VS Code, Copilot CLI y Copilot el 12 de agosto, aunque el texto también describe marketplaces específicos.

La portabilidad tiene límites: hooks, subagentes, permisos, UI y mecanismos de instalación siguen variando entre Claude, Codex, Copilot y otros clientes. El modelo recomendado mantiene Skill + MCP como núcleo y deja extensiones vendor-specific en el borde. El control de seguridad es explícito: descubrir, instalar, autorizar, habilitar y ejecutar son estados distintos; un plugin puede conectarse a un sistema con permisos que el agente no debe usar para borrar o escribir. Hay que revisar propietario, servidores, código local, permisos, Skills y operaciones de escritura. El autor no propone reescribir plataformas maduras ni convertir en plugin flujos que necesitan estado duradero, transacciones, eventos, UX rica o aislamiento estricto; sí ve una evolución de marketplaces de integraciones hacia registros de capacidades y resultados.

El texto la describe como un proyecto open source de Cheng Lou, creador de `react-motion`, con 44,2k estrellas y 2,4k forks en GitHub en el momento de la redacción, aunque el titular del digest usa el gancho de “50K Github Stars”. El problema que intenta resolver aparece al leer `getBoundingClientRect()` u `offsetHeight`: el navegador puede verse obligado a recalcular el layout, algo especialmente costoso con mucho texto cambiante.

Su API separa una preparación más pesada de layouts repetibles. `prepare()` segmenta el texto según reglas Unicode, mide cada segmento mediante Canvas y guarda los anchos; `layout()` usa esa caché para recalcular saltos de línea, número de líneas y altura a distintos anchos sin volver al DOM. El diseño sirve para chats con mensajes de altura variable, listas virtuales con miles de elementos, editores, whiteboards y herramientas documentales; también apunta a hilos de servidor o background donde no existe una página. El autor contrasta renderizar y medir —estable pero lento— con estimar por número de caracteres —rápido pero frágil ante idiomas, emojis y fuentes— y con limitar mediciones mediante caché, throttling y virtualización.

Pretext tiene licencia MIT y no ofrece un modelo comercial público; las posibles vías de monetización que se mencionan son especulativas, como consultoría, un motor más completo o convertirse en infraestructura de otro producto. No es un motor de layout completo: hay que cargar las fuentes antes, ciertas funciones avanzadas pueden ser inexactas y `system-ui` puede variar entre sistemas. El artículo conecta el caso con la adopción general de IA frontend: cita la encuesta Stack Overflow 2025 —84% usa o planea usar herramientas de IA y 51% de profesionales las usa a diario— y enumera Cursor, v0, Replit y Bolt como categorías que ya generan código, interfaces y aplicaciones, aunque la automatización total todavía no ha llegado.

Building an LLM From Scratch📖 Texto completo

Bernardo OlisanMedium26 de septiembre de 202656 min read
LLMCTransformersmachine learning

Bernardo Olisan explica un modelo de lenguaje construyendo uno pequeño en C desde cero, sin bibliotecas, PyTorch, NumPy, autograd ni GPU, sobre un MacBook Air M2 con 8 GB de RAM. El modelo tiene 1.258.240 parámetros frente a los 175.000 millones publicados para GPT-3. El recorrido empieza por distinguir IA, machine learning y deep learning, y compara las RNN —memoria comprimida en un vector y cálculo secuencial— con el Transformer de “Attention Is All You Need”, cuya paralelización encaja con las multiplicaciones de matrices de una GPU.
