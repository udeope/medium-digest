Stop Returning JSON. Start Shipping UI with MCP Apps📖 Texto completo

Andrii TkachukData Science Collective21 de septiembre de 202616 min read
MCPMCP Appsagentesinterfaces

Andrii Tkachuk sostiene que MCP ya resolvía bien la conexión entre un agente y una capacidad externa, pero se quedaba corto cuando el resultado necesitaba ser explorado o manipulado por una persona. Un JSON sirve para responder cuántos despliegues están activos; no basta para un dashboard, una tabla con filtros, un formulario de configuración, un gráfico o una aprobación humana. MCP Apps intenta cerrar esa brecha sin crear otro protocolo independiente: un MCP App combina una herramienta, un recurso de interfaz y un protocolo entre servidor, host y vista. El recurso puede ser HTML, JavaScript, React o Vue, y se renderiza en un iframe aislado mientras el host inyecta el resultado dinámico de la herramienta.

El artículo repasa la evolución que el autor atribuye a la extensión: SEP-1865 se presentó el 21 de noviembre de 2025, MCP Apps se anunció como extensión oficial el 26 de enero de 2026 con soporte inicial citado para ChatGPT, Claude, Goose y VS Code, y el release candidate de julio formalizó la negociación de capacidades y el modelo de extensiones. El flujo se parece al de una aplicación web, pero el agente dispara `tools/call`, el host lee el recurso `ui://`, renderiza la vista y le entrega los datos por JSON-RPC y `postMessage`. La interfaz puede llamar a otras herramientas a través del host, de modo que un botón de Restart usa la misma lógica de negocio que una acción del agente. El artículo recomienda pasar identificadores y versiones para rechazar aprobaciones obsoletas, y separar las herramientas visibles al modelo de las operaciones internas de la aplicación mediante `ui.visibility`.

La consecuencia arquitectónica es más importante que el widget: una sola operación puede tener una interfaz para la máquina y otra para la persona, evitando duplicar una API REST y una herramienta MCP para el mismo negocio. Los casos de uso más claros son operaciones, aprobaciones, búsqueda RAG con filtros, gobierno de agentes y formularios de configuración; no hace falta añadir una app a una respuesta que solo devuelve un número. El autor propone agrupar herramientas por dominio —por ejemplo, una app de gestión de despliegues— y adoptar primero una vista de solo lectura, después Refresh y finalmente una operación real. Advierte que el host debe implementar sandbox, permisos, negociación y proxy de llamadas, que el SDK oficial está centrado en TypeScript pero el backend puede seguir en Python, y que el iframe no es la frontera de confianza: autenticación, autorización, validación, auditoría, idempotencia y rate limiting siguen siendo responsabilidad del servidor.

I dreamed about moving the requirements specification to code.📖 Texto completo

Ilya ZakharauAnalyst's corner21 de septiembre de 20264 min read
SDDrequisitosdocs-as-codedesarrollo con IA

Ilya Zakharau parte de un problema conocido en proyectos grandes: tareas, documentación, requisitos y código viven en Jira, Confluence, GitHub o GitLab, y rara vez conservan una imagen coherente cuando cambia la persona que los mantenía. El autor simpatiza con docs-as-code porque pone la documentación de servicio en Markdown junto al código y la actualización puede formar parte de la definición de terminado. Pero su experimento mental tropieza con los requisitos que atraviesan varios módulos o repositorios: no encajan limpiamente en un archivo de arquitectura y un repositorio separado de requisitos le parece incluso peor que Confluence.

La llegada de los agentes cambia el valor relativo de cada artefacto. La especificación puede quedar obsoleta con independencia del desarrollo y, al mismo tiempo, el código se vuelve barato y regenerable con un prompt. Por eso el texto busca una fuente de verdad determinista dentro de un entorno donde la salida de la IA es indeterminista. Spec-Driven Development coloca una especificación estructurada en el centro para que un agente genere código; la idea no es completamente nueva, porque OpenAPI y otros lenguajes específicos de dominio ya producen capas de software desde contratos formales. La diferencia está en la escala y en que el agente puede generar casi cualquier cosa, limitado por la calidad del contexto y por el coste de los tokens.

El desplazamiento también cambia el trabajo de requisitos: leer documentos pasa a ser ingeniería de prompts y de contexto para introducir un contrato consumible por la máquina. El autor quiere que la especificación permanezca sincronizada con la implementación y tenga trazabilidad, pero no presenta SDD como una victoria limpia. PRD y BRD pueden seguir existiendo para humanos durante un tiempo, mientras pasar un documento de negocio entero a un LLM para generar código se considera un antipatrón. OpenSpec, MUSUBI, Spec-Kit y Superpowers aparecen como ejemplos de una lista que puede cambiar pronto. El cierre es una observación crítica: SDD revive en un momento en que las empresas buscan una ilusión de control y eficiencia, no necesariamente el futuro de requisitos que el autor había imaginado.

How to Build a McKinsey-Style PowerPoint with AI: 8 Simple Rules for…📖 Texto completo

Sylvia ChenPublicación no indicada21 de septiembre de 20268 min read
PowerPointpresentacionesconsultoríaTosea AI

Sylvia Chen aclara que una presentación “al estilo McKinsey” no se define por fondo blanco, azul oscuro o una tipografía concreta, sino por una disciplina de comunicación. La presentación debe decidir primero qué decisión apoya, exponer pronto la conclusión, asignar una tarea principal a cada diapositiva, aportar evidencia verificable y dejar claro qué debe ocurrir después. La primera regla es construir el argumento antes de abrir PowerPoint: una conclusión, los argumentos que la sostienen y la evidencia de cada uno. La segunda convierte títulos temáticos como “Market growth” en títulos de acción que expresan qué demuestra el análisis.

Las ocho reglas siguen esa lógica. Cada página debe responder a una pregunta única aunque contenga gráfico, interpretación, fuentes y recomendación; el formato visual debe corresponder a la relación de la información —proceso, ciclo, jerarquía o conexión—; y los gráficos deben ser evidencia, no decoración. La guía aconseja eliminar series y etiquetas que no ayuden, destacar la prueba principal con un color de acento, registrar organización, documento, fecha y página de cada cifra, y conservar una cuadrícula, márgenes y jerarquía estables. También recuerda el umbral de contraste que cita del W3C, 4,5:1 para texto normal y 3:1 para texto grande. La revisión se separa en tres pasadas: leer solo títulos, validar números y fuentes, y revisar después alineación, tipografía, color y exportación.

La segunda mitad presenta Tosea AI como herramienta de presentaciones basada en fuentes. Según el artículo, puede transformar PDFs, informes, investigaciones y otros documentos en diapositivas editables, proponer layouts y diagramas durante el esquema, cambiarlos después de renderizar y exportar un PPTX editable donde texto, formas, iconos y estructuras se recuperan cuando es posible. El ejemplo de prompt pide una historia de conclusión primero, una idea principal por página, preservación de fuentes y aprobación del esquema antes de renderizar. El caveat es explícito: el texto no está afiliado ni respaldado por McKinsey, y las páginas complejas, fuentes corporativas o gráficos intrincados siguen necesitando revisión final. La tesis útil no es imitar una marca, sino construir un sistema repetible para decisiones, evidencia y revisión.

En segundo, los enlaces de fuente no trasladan automáticamente la responsabilidad al usuario. En tercero, el resumen de IA es una función opcional, no una necesidad técnica de la búsqueda tradicional, así que Google elige asumir el riesgo cuando la inyecta en la página. El artículo también menciona los 275 dólares que el autor gastó probando Veo 3 como ejemplo de la distancia entre marketing y fiabilidad. El caveat legal importa: se trata de una resolución preliminar, Google puede recurrir y el marco europeo no coincide con las protecciones de intermediarios de Estados Unidos, incluida la Sección 230. Por tanto, el texto presenta una dirección de responsabilidad y rendición de cuentas, no una sentencia final ni una regla universal aplicable a todos los sistemas de respuesta.

Hao Yu cuenta un experimento en el que pidió a Fable 5.1 y GPT-6 Astra que le hicieran millonario y terminó construyendo un laboratorio de investigación de trading llamado BoringAlpha, no un bot para dinero real. La ambición inicial de ganar un 5% semanal era una broma; el plan prudente era empezar con paper trading y quizá poner entre 2.000 y 5.000 dólares más adelante. Los modelos repartieron el trabajo de diseño, implementación y revisión, pero el proyecto acumuló 1.044 tests sin producir un yate. La tesis práctica es que una ingeniería cada vez más pulida no convierte por sí sola una hipótesis de inversión en una ventaja.

BA-001 repartía por igual una cuenta entre ocho ETF —acciones, bonos del Tesoro, oro y materias primas— y, al cierre de cada mes, mantenía cada activo solo si había superado al efectivo durante los doce meses anteriores. Se desarrolló con datos de 2007–2017 y se validó en 2018–2021. Redujo drawdown, pero un control que simplemente mantenía menos de todo ganó más: 5,84% anualizado frente a 3,63% de la estrategia, con mejor Sharpe. La revisión posterior incorporó contabilidad fiscal por lotes, ventas con pérdidas y ocho escenarios, sin cambiar la conclusión. BA-001 quedó “inconclusive”: no perdió el dinero simulado, pero no justificó ser usado.

BA-002 combinó señales de 9, 12 y 15 meses y se comparó con invertir 60% en los mismos ocho ETF y dejar 40% en efectivo, rebalanceando una vez al año. La exigencia era superar al rival en 0,5 puntos porcentuales después de impuestos, mantener drawdown de 20% o menos y resistir la comparación en dos fuentes de datos. La comprobación Yahoo/Tiingo detectó una distribución de un ETF ausente en Yahoo; se confirmó con el emisor y se documentó la corrección. Aun así, el benchmark rindió aproximadamente 5,45% antes de impuestos frente a 2,70% de BA-002 y tuvo menor drawdown, 12,18% frente a 13,70%, en el periodo posterior. BA-003 queda como borrador de momentum 12–1 con una ponderación desigual de la parte de acciones. El autor seguirá investigando, pero no financiará un bot: son simulaciones históricas bajo supuestos declarados, no asesoramiento ni previsión.

The curse of Big Tech: how digital giants are eroding the constitutional…📖 Texto completo

El artículo firmado por la European Court of Auditors y escrito por Reijer Passchier presenta la concentración de poder tecnológico como un problema constitucional, no solo como una cuestión de privacidad o competencia. Reconoce que Microsoft, Amazon, ByteDance y otros actores han aportado conveniencia, eficiencia y entretenimiento barato, pero sostiene que su tamaño también presiona la soberanía estatal, la separación entre esfera pública y privada, el Estado de derecho, la ciudadanía política y la propia idea de gobierno limitado. La pregunta central es cuánta resiliencia necesita la Unión Europea para conservar su identidad democrática cuando infraestructuras y decisiones dependen de empresas estadounidenses y chinas.

A ello suma la dependencia europea de nubes y plataformas para medicina, finanzas y seguridad, y una relación geopolítica en la que la capacidad estadounidense de acceder a infraestructuras cloud puede convertirse en palanca. El artículo advierte incluso de que leyes protectoras pueden perjudicar proporcionalmente más a competidores pequeños que a los incumbentes.

Menciona Nextcloud, Fairphone y Proton como ejemplos de open source y steward ownership, y Signal como estructura sin ánimo de lucro; también plantea formas de propiedad distribuida. Es un ensayo normativo apoyado en referencias académicas, regulatorias y periodísticas: sus afirmaciones sobre lobbying, geopolítica y erosión constitucional expresan la tesis del autor y deben leerse junto con las fuentes citadas, no como una medición neutral de todos los efectos de Big Tech.

Context Graphs for AI Agents: Giving AI the Memory of a Senior Engineer📖 Texto completo

Vaibhav KashyapPublicación no indicada21 de septiembre de 202622 min read
Context GraphagentesGraphRAGmemoria

Vaibhav Kashyap plantea los Context Graphs como una forma de dar a los agentes la memoria conectada de un ingeniero senior. El ejemplo inicial es un repositorio de cinco años con 40 microservicios, miles de clases, tablas, tickets, pull requests, reglas de seguridad y habilidades: un agente puede encontrar un controlador parecido y compilar código, pero ignorar reglas dispersas sobre `OrganizationID`, `TenantID`, permisos financieros, orquestadores o incidentes anteriores. Un Context Graph organiza entidades, relaciones, estado, historia y decisiones para que el agente conozca no solo qué existe, sino cómo se conecta, qué pasó antes y por qué se eligió una arquitectura. El autor avisa de que el término todavía está evolucionando y no es un estándar técnico único.

La diferencia frente a un Knowledge Graph es el contexto operativo: intención del usuario, permisos, estado actual, validez temporal, procedencia y trazas de decisión. El grafo puede enlazar controlador, servicio, repositorio, tabla, endpoint, ADR, incidencia, test, commit y pull request, con propiedades de fecha y confianza. Para crear un endpoint, el agente identifica nodos iniciales, expande relaciones, filtra por rama, módulo, versión, organización y permisos, y construye un paquete pequeño con patrón arquitectónico, seguridad, tenancy, base de datos, tests y decisiones relevantes. El texto no propone sustituir la búsqueda vectorial: recomienda combinar vector search para descubrir, palabras clave para nombres exactos, recorrido de grafo para importancia conectada y razonamiento del agente; esa combinación se acerca a GraphRAG.

La propuesta práctica es empezar con un repositorio y una skill, quizá diez tipos de nodo —módulo, clase, endpoint, servicio, repositorio, tabla, regla, permiso, test y ADR— y actualizar de forma incremental con los archivos cambiados. Un primer experimento puede usar Neo4j, o algo más pequeño como JSON, NetworkX y SQLite, detrás de una API o servidor MCP con operaciones como `get_context_for_task` y `record_decision`. El grafo debe distinguir hechos, observaciones, inferencias, decisiones y reglas, incluir confianza y permitir corrección humana; un contexto equivocado se convierte en otra fuente de alucinación. La promesa final es que código, skills y contexto formen tres capas, pero el artículo sigue siendo un diseño conceptual: no ofrece una evaluación comparativa de producción ni demuestra que el grafo sustituya a la revisión humana o a los modelos de recuperación existentes.

I spent two months building an AI workflow for my design team. Here's what I…📖 Texto completo

La autora de Tripadvisor Tech describe dos meses intentando introducir IA en el trabajo diario de un equipo de diseño B2C. Su descubrimiento inicial fue que el problema no era simplemente “adoptar IA”, sino la fragmentación: cada persona reinventaba procesos en silencio. La solución experimental fueron skills reutilizables de Claude, es decir, prompts estructurados que codifican conocimiento del equipo y ofrecen contexto específico. El caso que mejor funcionó fue el de los project briefs, una tarea que todo el mundo considera necesaria y que una skill podía volver más rápida. También creó generadores de ilustraciones con estética 3D de arcilla para Tripadvisor y Viator, y probó alrededor de 100 ilustraciones sobre un proyecto real antes de compartirlos.

El trabajo técnico fue más amplio de lo previsto. Hubo que enseñar Git a diseñadores que nunca habían usado un terminal, construir buenas prácticas de Claude Code y skills de despliegue, y resolver que los prototipos internos estaban detrás de la VPN. La infraestructura de alojamiento externo convirtió “funciona en mi máquina” en un enlace que podía probar una persona real, con prototipos interactivos en lugar de maquetas de Figma. Sin embargo, conseguir adopción resultó más difícil que construir: un mensaje en Slack podía recibir silencio porque usar una herramienta nueva exige recordarla, encontrar una tarea adecuada, confiar en ella y entender la documentación.

El artículo concluye que la tecnología no fue el cuello de botella; lo fueron documentación, control de versiones, comunicación y tiempo de ingeniería. Las skills que sobrevivieron tenían una descripción honesta, instrucciones para quien sabía menos y acompañamiento personal; las que solo se dejaron en el repositorio se apagaron.
