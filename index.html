How did YouTube engineers build CI/CD for data pipelines?📖 Texto completo

Vu TrinhData Engineer Things1 de septiembre de 202610 min read
CI/CDdata engineeringpipelinescalidad de datos

El artículo resume el trabajo de los ingenieros de YouTube sobre CI/CD para pipelines de datos, a partir del paper «Unlocking the Power of CI/CD for Data Pipelines in Distributed Data Warehouses». La escala condiciona todo: el almacén coordina miles de pipelines cada día, procesa varios exabytes y versiona cada partición temporal de forma independiente para poder actualizarla o revertirla sin afectar a las demás. Para incorporar un pipeline, la plataforma recibe configuración de scheduling y dependencias, reglas de almacenamiento y replicación, parámetros de producción y la lógica de transformación escrita en SQL u otros lenguajes.

El autor separa los problemas que hacen distinta a la CI de datos de la CI de software: hay que validar volumen, variedad, esquema, semántica, calidad y relaciones entre activos; replicar fuentes, sistemas distribuidos y hardware de producción sería demasiado caro; además aparecen cuellos de botella de despliegue, observabilidad distribuida, seguridad y coordinación entre equipos. La solución combina configuraciones de prueba para aislar subgrafos, un Configuration Rewriter que reutiliza y adapta la configuración productiva, gestión de datos con enmascarado, datos sintéticos y versionado, un Controller que orquesta el entorno completo y herramientas de diagnóstico y reporting.

El framework añade profiling, reglas de calidad generadas desde propiedades de los datos y detección de anomalías, junto con un metadata hub que centraliza dependencias, métricas y configuraciones. El muestreo puede reducir el volumen un 99,9% y llevar una prueba de más de un día a casi una hora; investigar integraciones baja un 50% y los cambios de esquema pasan de semanas o meses gracias a conocer el impacto downstream. El takeaway es no quedarse en unit tests: conviene combinar diffs, integración y end-to-end, IaC, trazas, lineage, alertas, hipótesis estadísticas y datos de prueba realistas, enmascarados y reproducibles.

8.2 minutes, and you will understand how most data systems execute joins.📖 Texto completo

Vu TrinhData Engineer Things1 de septiembre de 202610 min read
bases de datosSQLjoinsOLAP

El texto explica cómo se ejecutan físicamente los joins que el SQL oculta detrás del optimizador. Se limita a los equi-joins, es decir, combinaciones que comparan columnas con `=`, y distingue la tabla izquierda de la derecha. El nested loop join recorre cada fila de la izquierda y vuelve a explorar la derecha; es simple y no necesita estructuras auxiliares, pero puede ser muy costoso. El block-nested loop reduce el I/O leyendo un bloque de la izquierda en memoria y recorriendo una vez la derecha, mientras un índice sobre la clave puede convertir cada búsqueda en un lookup. Por eso funciona mejor cuando la izquierda es pequeña o la derecha está indexada.

El sort-merge join tiene una fase de ordenación de ambas tablas y otra de avance sincronizado de punteros. Combina las claves iguales, genera todas las combinaciones cuando hay duplicados y avanza el puntero de la tabla con el valor menor. El coste extra de ordenar puede compensar si los datos ya están ordenados, tienen índices clustered o la salida debe quedar ordenada. El hash join, en cambio, construye una tabla hash con la tabla menor y después la sondea con la otra; es especialmente eficaz para equi-joins, pero pierde rendimiento si la estructura no cabe en memoria y empieza a derramar particiones al disco.

Para ese caso aparece Grace Hash Join: particiona ambas tablas por hash en buckets de disco, vuelve a particionar los que aún son demasiado grandes y procesa cada pareja en memoria. En OLAP, donde ambos lados son grandes y normalmente no hay índices de lookup, los sistemas distribuyen esos buckets entre workers y deben vigilar el skew de una clave muy frecuente. El artículo indica que Snowflake usa hash en la mayoría de casos, BigQuery solo hash y Spark hash o sort-merge; además, todos pueden aprovechar un broadcast join cuando una tabla pequeña cabe en memoria. El consejo práctico es mirar estadísticas, I/O, distribución de claves y estrategia elegida al depurar una consulta lenta.

Rendering 100,000 Rows Efficiently in Angular📖 Texto completo

Roshan NavaleCodeToDeploy1 de septiembre de 20267 min read
Angularrendimientovirtual scrollingfrontend

El problema de renderizar 100.000 filas en Angular no es almacenar el array, sino convertirlo en una enorme estructura DOM que el navegador debe medir y que Angular debe revisar. Más nodos implican más memoria, renderizado inicial más lento, más trabajo de layout y change detection, peor scroll y una experiencia frágil. La primera decisión es no mostrarlo todo: para una aplicación empresarial, la paginación del servidor puede devolver 25, 50 o 100 registros por página mediante parámetros como `page` y `pageSize`, además de evitar descargar datos que el usuario nunca consultará.

Cuando se necesita scroll continuo, el autor propone `CdkVirtualScrollViewport` y `*cdkVirtualFor`: la ventana solo dibuja las filas visibles y un buffer, reutilizando el área renderizada a medida que el usuario se desplaza. `trackBy` con un identificador estable como `user.id` evita recrear nodos cuando se refrescan, insertan, eliminan, ordenan o filtran objetos. `OnPush` limita comprobaciones a referencias y eventos relevantes. El texto también recomienda precalcular valores costosos en vez de llamar funciones caras desde la plantilla, agrupar peticiones asociadas a las filas y no hacer una llamada API por cada elemento.

La arquitectura debe repartir el trabajo: filtrado, ordenación y paginación en el servidor; en el cliente, solo la ventana actual y filas ligeras. Imágenes con `loading="lazy"`, thumbnails y CDN reducen peso, mientras que demasiados componentes anidados, pipes, subscriptions o handlers multiplicados por miles de filas pueden anular la ganancia. La estrategia final combina consulta server-side, API paginada, virtualización y componentes sencillos; para conjuntos menores, la paginación normal basta. Antes y después hay que medir tiempo inicial, memoria, número de nodos, scroll, actividad de change detection, payload, respuesta API y complejidad de cada fila: virtual scrolling no arregla por sí solo un backend lento.

We Rewrote Our API in Rust for 20% Better Performance. It Cost Us $180K.📖 Texto completo

Aditya SuryawanshiLevel Up Coding1 de septiembre de 20268 min read
RustGoZigbenchmarks

El experimento nace de un benchmark que decía que Rust era tres veces más rápido que Go y de una migración que costó cuatro meses y unos 180.000 dólares antes de descubrir que, en el API real, Go rendía mejor para el equipo y el hardware disponibles. Para comprobarlo, el autor implementó tres veces el mismo endpoint `POST /api/orders`: valida JSON, comprueba el token en Redis, escribe en PostgreSQL y devuelve JSON estructurado. Mantuvo iguales la base de datos, los payloads, el hardware y la carga, y midió latencia, throughput, memoria, arranque, tamaño del binario y tiempo hasta el primer resultado correcto.

Con 1.000 peticiones concurrentes, PostgreSQL en red local y Redis caliente, Rust obtuvo p50 de 4,2 ms, p99 de 11,3 ms y 18.400 req/s; Go, 5,1 ms, 14,7 ms y 15.200 req/s; Zig, 4,8 ms, 12,1 ms y 16.900 req/s. La memoria en reposo fue de 8,4, 22,1 y 6,1 MB, y bajo carga de 94, 187 y 71 MB, respectivamente. Los binarios midieron 4,2, 7,8 y 1,9 MB; los arranques tardaron 12, 31 y 8 ms. Pero el primer test integrado que pasó llegó en 3,5 días con Rust, 4 horas con Go y 6 días con Zig: el lenguaje de mayor throughput no ganó la métrica de entrega.

La conclusión es contextual. En un API limitado por I/O, la ventaja de Rust frente a Go rondaba el 20%, mientras la productividad para un equipo que conocía Go podía ser diez veces mayor; si una consulta tarda 45 ms, optimizar el lenguaje no ataca el cuello de botella. El equipo de ocho personas en tres zonas horarias terminó enviando Go, dejó Rust en una rama y descartó Zig para web por ser pre-1.0. Rust encaja si la corrección o el cómputo CPU son críticos; Zig, en compiladores, sistemas u otros usos cercanos al metal. El caveat es esencial: son resultados de una carga, un hardware y un equipo concretos, no una clasificación universal.

El marco tiene cuatro capas. El design system es el contenedor y debe exponer tokens CSS, escalas de espaciado, ejemplos y nombres semánticos; la arquitectura va de primitivas a tokens de propósito y componentes compuestos.
