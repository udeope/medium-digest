Redesigning the Idea Lab Website📖 Texto completo

DaguilarMacalester HCI12 de octubre de 202617 min read
UXprototipadoWordPressaccesibilidad

El proyecto de Rachel Xu, Sidney Greene y Daniel Aguilar parte de una crítica concreta al sitio del Idea Lab de Macalester College: la información existe, pero está repartida en secciones repetitivas, enlaces poco visibles y módulos que no ayudan a distintos tipos de usuario a orientarse. El menú “What You’ll Find” escondía frases únicas en desplegables; el enlace a Instagram solo hacía interactivo el símbolo @; el Google Calendar mensual aparecía demasiado denso; el contacto fallaba en algunos dispositivos; y la zona de noticias apilaba elementos que conducían a la misma historia. El equipo también tuvo que aceptar que los bloques disponibles en WordPress limitaban cambios estructurales importantes. Por eso no diseñó una única solución, sino tres prototipos con grados crecientes de restricción, todos guiados por la idea de mejorar la navegación sin borrar la personalidad colaborativa del laboratorio.

La fase de papel convirtió el espacio en un tablero de corcho interactivo, con información que podía aparecer como un cartel fijado, y exploró un mapa del laboratorio. Para que la prueba se pareciera a usar un ordenador construyeron una pantalla de cartón, hicieron pasar las hojas como si fueran scroll y usaron velcro para los pop-ups. Probaron los diseños con estudiantes de primer curso, profesorado y personal estudiantil, asignando tres tareas a cada grupo. Descubrieron que el prototipo restringido permitía volver atrás con facilidad, pero no dejaba claro qué había detrás de la página inicial; el libre era más fácil de recorrer, aunque podía resultar abrumador. Las expectativas de los usuarios también desafiaron la arquitectura: calendario bajo “eventos” y mapa bajo “recursos” no eran ubicaciones obvias, mientras que un botón de reserva visible sí respondía a una necesidad real del profesorado y del personal.

En Figma, el diseño no restringido usó una paleta vinculada a Macalester, widgets para noticias y calendario, páginas de mapa, materiales, tutoriales y personal, y módulos separados para personal fijo y estudiantes. La única ayuda de IA mencionada fue el agente integrado de Figma, usado para crear módulos de personal y noticias por falta de tiempo. El diseño semirrestringido partió de un primer borrador de Claude, pero requirió correcciones manuales en barra lateral, organización y navegación; añadió una barra siempre visible, calendario semanal por defecto y una pantalla intermedia antes de enviar a EMS. En WordPress reutilizaron bloques existentes, alojaron el mapa en GitHub dentro de un iframe fijo de 800×600 y conservaron el calendario conectado a sus API, con la limitación de que el mapa no era responsive. Las pruebas de alta fidelidad llevaron a mejorar contraste, textos alternativos y tamaño de indicadores, aunque quedó un problema con fondos amarillos y el prototipo libre no pudo incluir alt text. El equipo concluye que la iteración con usuarios fue decisiva, pero reconoce que faltaron alumni, donantes y otros públicos, además de tiempo y contenido para cerrar el producto.

How To Run Claude Like a Tech Lead, Not a Senior Engineer📖 Texto completo

Jerry PMCodeToDeploy12 de octubre de 202611 min read
Claude Codeagentes IAworktreesliderazgo técnico

Jerry PM sostiene que usar Claude Code como un único asistente muy rápido es quedarse en el nivel de colaborador individual: cuando aparecen varias tareas simultáneas, la habilidad necesaria se parece más a dirigir un equipo técnico. Cuenta que llegó a mantener cuatro sesiones abiertas —una construía una función, otra probaba el simulador de iOS, otra trabajaba en una migración desde un worktree y otra revisaba un pull request— sin escribir código ni volver a hacer un briefing único. Su primer cambio mental es abrir `claude agents` y mirar qué está bloqueado, qué termina y qué necesita una decisión, en lugar de concentrarse en un terminal. Propone dividir un ticket en sesiones con funciones distintas: una sesión Developer recibe el PRD y construye; otra QA instala el arnés del simulador, recorre la aplicación y busca fallos. La separación importa porque quien escribió el código es el peor revisor de sus propias decisiones.

El artículo presenta la comunicación entre sesiones mediante `ListAgents` y `SendMessage`, menciones con `@`, `Ctrl+O` para desplegar mensajes y `/list-agents` para saber quién está disponible; según el autor, el sistema llegó también a Windows nativo a finales de agosto. Distingue un fork de una sesión nueva: `/subtask` sirve para una tarea lateral que necesita toda la conversación y la caché de contexto, como redactar tests de lo que se acaba de construir; una sesión paralela debe tener problema y contexto propios. Para evitar que cuatro agentes editen la misma copia, recomienda worktrees, que también bloquean comandos y redirecciones Git hacia el checkout principal. Las sesiones de fondo pueden confirmar y subir sus cambios, abrir un PR en borrador cuando corresponda y seguir las políticas de `CLAUDE.md`. En vez de reescribir el mismo rol, propone archivos en `.claude/agents/` con `tools` como lista de permisos, `model`, `effort`, `isolation` y `maxTurns`; así un revisor puede leer y analizar sin tener permiso de modificar.

Las guardas deben preceder a la escala. Claude parte de un límite de 20 subagentes concurrentes y el autor muestra `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS=30` como ajuste explícito; también sugiere limitar la profundidad de anidamiento, mantener permisos estrechos para dinero, autenticación y persistencia, y asignar el nivel de esfuerzo según la dificultad. El problema central no es cuántas sesiones caben, sino cuántos diffs puede leer de verdad el responsable: su cifra personal es tres, a veces dos o una en días con reuniones. Recomienda ejecutar `/code-review` o `/review` en paralelo y usar `/ultrareview` para una mirada fresca, pero recalca que el humano sigue firmando el commit. El flujo final es revisar sesiones antiguas, planificar, construir en un worktree, levantar QA, usar forks para tareas con contexto, comunicar cambios de esquema, revisar cada diff y solo después confirmar. La limitación que reconoce es importante: al empezar con cuatro sesiones entregó menos que con una porque no alcanzaba a revisar todo.

Following China's Long March: Wumeng Mountain 330k Trail📖 Texto completo

Harriet GaywoodRunner's Life12 de octubre de 202610 min read
ultratrailChinaLarga Marcharesistencia

Harriet Gaywood utiliza una carrera de ultratrail para recorrer una parte de la memoria histórica de China. La Gran Marcha de 1934–35 se describe como un desplazamiento de 12.500 kilómetros iniciado por unos 80.000 soldados del Ejército Rojo, de los que sobrevivieron aproximadamente 8.000–9.000; el episodio se convirtió en mito revolucionario y contribuyó al ascenso de Mao Zedong. Noventa años después, la autora se inscribe en la Wumeng Mountain 330k Trail Race, organizada en torno a rutas de esa zona de Yunnan. El recorrido anunciado sumaba 330 kilómetros y 16.500 metros de desnivel, empezaba en Zhaotong, a unos 2.000 metros, y exigía avanzar en grupo alrededor de 60–70 kilómetros diarios. La narración mezcla contexto histórico, paisaje y una duda inicial muy práctica: no tenía equipo ni sabía si podría mantener el ritmo de desconocidos durante tantos días.

El grupo acaba siendo de once personas y atraviesa aldeas, huertos de manzanos, plantaciones de tabaco, mezquitas, minas de carbón abandonadas y caminos rurales bajo lluvia persistente. El apoyo logístico es decisivo: los checkpoints ofrecen leche de soja, mantou, arroz y verduras calientes; la responsable de operaciones insiste en comer suficiente arroz y restringe los geles por el riesgo digestivo y la falta de acceso por carretera. Solo dos corredores llevan el GPX, hay tramos de noche con barro, desprendimientos y senderos cubiertos de vegetación, y el descanso se reduce a siestas de una a cuatro horas en granjas, casas de huéspedes u hoteles sencillos. El itinerario pasa por el memorial de la Larga Marcha en Kuixiang, zonas de “turismo rojo”, cultivos, una aldea Miao y cumbres de 3.100–3.500 metros. La autora observa también el desarrollo desigual de la región: una fábrica solar nueva junto a viviendas aisladas, mercados locales, caminos perdidos y la presencia de niños cuyos padres trabajan en las ciudades.

Tras cinco días llega al final de su tramo de 330 kilómetros después de vadear un río; otros participantes ya habían registrado más de 350 y continuaban hacia 500. La estrategia real no fue correr rápido, sino “run, walk, rest, repeat”, acompañada de comida, cooperación y adaptación. En el equipamiento menciona dos pares de Kailas FUGA, una chaqueta Gore-Tex, capas de merino y leggings, guantes, chaqueta de plumas, tres frontales Nitecore y baterías de 10.000 y 20.000 mAh guardadas en bolsas Ziploc; el reloj Coros no pudo registrar toda la ruta porque cargarlo obligaba a detener el tiempo. La experiencia no pretende ser una guía de entrenamiento ni un resultado deportivo comparable: es un diario de una prueba extrema en terreno remoto, donde la poncho prestada, el trabajo del grupo y la logística de los checkpoints importan tanto como la resistencia física.

I Bought Friendster for $30k - Here's What I'm Doing With It📖 Texto completo

Mike Carson12 de octubre de 20265 min read
Friendsterdominiosredes socialesproducto

Mike Carson cuenta cómo terminó comprando el dominio `friendster.com` y qué intenta hacer con una marca que había desaparecido. Friendster, una de las primeras redes sociales, dejó de funcionar en 2015 y cerró oficialmente en 2018. El dominio, registrado originalmente el 22 de marzo de 2002, volvió a resolver en 2023 con anuncios emergentes. Carson descubrió que lo tenía un cliente de Park.io y que lo había adquirido en una subasta de dominios expirados de gname.com por 7.456 dólares. El propietario pidió 40.000; Carson ofreció 20.000 y acabó cerrando un intercambio de 20.000 dólares en bitcoin más un dominio que generaba unos 9.000 dólares anuales en publicidad. Después consultó a abogados y recibió el 13 de mayo de 2025 la confirmación de que también controlaba las marcas Friendster.

El primer intento fue construir una red social básica en el dominio e invitar a personas de una lista de espera. La propuesta de no vender datos, no usar algoritmos y no mostrar anuncios no produjo suficiente entusiasmo, así que Carson publicó el proyecto en Hacker News. El comentario que más le influyó proponía que la amistad se verificara tocando físicamente dos teléfonos: una acción que obliga a encontrarse, comprueba que las personas son reales y separa la idea de una red social puramente remota. A partir de ahí creó una aplicación para iOS en la que la conexión de amistad requiere ese contacto en persona. La revisión de Apple tardó entre uno y dos meses, pero la aplicación finalmente apareció en la App Store. El autor dice que no está centrado en ganar dinero y que quizá ofrezca un plan de pago para que el servicio se sostenga más adelante.

Las funciones que está explorando intentan convertir la red en un recordatorio de relaciones presenciales. “Friends of friends” permite ver amistades de segundo grado y pedir contacto; “fading connections” suaviza el vínculo si pasa un año sin volver a tocar teléfonos, como una señal de que una relación necesita atención y no como castigo. Carson vincula el proyecto a su propia historia: conoció a su esposa en OkCupid y considera que las plataformas pueden cambiar la vida de las personas. El texto no aporta métricas de adopción, costes operativos ni pruebas de que la mecánica resuelva la falta de interés inicial; es una explicación de producto y motivación personal. Su apuesta es deliberadamente pequeña: si Friendster ayuda a unas pocas personas a encontrar una conexión real, el dominio y el experimento habrán valido la pena.

Popular Programming Languages for Web Development in 2026📖 Texto completo

Aditi Grover12 de octubre de 20267 min read
programaciónwebTypeScriptPython

Aditi Grover sostiene que elegir lenguaje para desarrollo web en 2026 ya no consiste en escoger un único sucesor de JavaScript o PHP. Hace una década el camino parecía más lineal; ahora JavaScript cubre frontend y backend, TypeScript se ha convertido en una opción central, Python está unido a IA y datos, y Go y Rust aparecen en infraestructura y software sensible al rendimiento. Cita datos de GitHub según los cuales TypeScript pasó a ser el lenguaje más usado en agosto de 2025, por delante de Python y JavaScript, con más de un millón de contribuidores adicionales durante el año. En paralelo, Python seguiría dominando los repositorios de IA y cerca de la mitad de los proyectos nuevos de IA lo usarían como lenguaje principal. La lectura del autor no es sustitución, sino diversificación y combinación de stacks.

El repaso práctico comienza por Python, apoyado en IA, machine learning, ciencia de datos, automatización y frameworks web como Django y FastAPI. JavaScript mantiene su lugar en aplicaciones frontend, servicios, APIs y tiempo real; TypeScript añade tipado estático y herramientas para mantener aplicaciones grandes. Java sigue siendo relevante en empresa, finanzas y sistemas de larga vida; PHP conserva una base real en webs, CMS, comercio electrónico y Laravel; Go encaja en APIs, nube, redes y backend; Rust destaca por rendimiento y seguridad de memoria, y aparece como el lenguaje más admirado en la encuesta de Stack Overflow 2025, con un 72% de intención de continuidad entre quienes lo habían usado. Ruby y Rails completan la lista como ecosistema establecido, aunque menos visible en la conversación actual. El texto insiste en que popularidad y novedad no son lo mismo que utilidad.

La recomendación final depende del problema: JavaScript y TypeScript para frontend, Python para IA, datos o backend, Java o C# para empresa, PHP para Laravel y WordPress, Go para servicios cloud y Rust para sistemas y rendimiento. El artículo enumera combinaciones como TypeScript + React + Node.js, Python + Django, PHP + Laravel y Java + Spring para recordar que el lenguaje es solo una capa. También menciona que el 84% de encuestados en Stack Overflow 2025 usa o planea usar herramientas de IA, pero advierte que generar código no equivale a entenderlo. La sugerencia para quien empieza es escoger algo, construir, atascarse, arreglarlo y después aprender otra cosa; el caveat central es que ninguna cifra de adopción decide por sí sola una carrera, porque el objetivo, el ecosistema y la capacidad de aprender pesan más que perseguir el lenguaje de moda.

How we built the new Table of Contents feature📖 Texto completo

Scott BatsonMedium Engineering12 de octubre de 20268 min read
MediumUXfrontendnavegación

Scott Batson explica cómo Medium convirtió una vieja extensión de Chrome en una función nativa de tabla de contenidos. La extensión ya demostraba que muchos lectores querían orientarse en historias largas, pero tenía problemas de diseño y mantenimiento: insertaba una lista dentro del artículo, mutaba el contenido que el escritor había creado, quedaba obsoleta si se añadían encabezados y solo podía usarse desde la parte superior. La solución nueva conserva la misma fuente de verdad —los encabezados del cuerpo—, pero genera el índice al renderizar la página final. Esto es relevante porque Medium no guarda simplemente un documento terminado: combina revisiones para construir la versión que recibe el lector. El artículo describe una función que se deriva del resultado visible, no una lista que el autor tenga que mantener a mano.

El primer prototipo nativo volvió a colocar la tabla en el menú de tres puntos, pero las pruebas mostraron que el lector seguía teniendo que regresar arriba. El diseño evolucionó a indicadores en el margen derecho que acompañan el scroll, distinguen encabezados principales y secundarios mediante líneas de distinto tamaño, resaltan en verde la sección actual y permiten desplazamiento suave. La implementación debe tratar casos extremos: una imagen que ocupa todo el ancho necesita fondo translúcido; un texto con un solo encabezado oculta el índice porque no aporta valor; una historia con cien encabezados usa una ventana deslizante para no desbordar la página. En móvil, el margen es demasiado estrecho y los indicadores invadirían el texto, así que el equipo decidió desarrollar otra solución específica en lugar de encoger la versión de escritorio.

El resultado buscado es dinámico, accesible desde cualquier punto, suave al navegar y sin añadir contenido al post. Medium puede medir el uso de la función, algo que la extensión no permitía de la misma forma. Batson también responde a la preocupación de que saltar por el texto perjudique ingresos: afirma que Medium no calcula las lecturas válidas a partir del comportamiento de scroll, y que facilitar la navegación puede mejorar la retención. El desarrollo tomó un par de días, con buena parte del tiempo dedicado a probar la experiencia y ajustar el diseño, no a la complejidad del código. La lección práctica es separar la herramienta del lector del contenido del escritor y dejar que el documento real genere la navegación; el límite es que la solución móvil todavía queda pendiente en el texto.

Why Did You Stop Doing the Thing You Loved?📖 Texto completo

Jud Brewer MD PhD12 de octubre de 202612 min read
motivaciónpsicologíacuriosidadburnout

Jud Brewer usa la pregunta del título para revisar cómo se transforma una actividad querida cuando cambian sus recompensas. Parte de la diferencia clásica de la Self-Determination Theory de Edward Deci y Richard Ryan: la motivación intrínseca obtiene su recompensa de la propia actividad, mientras que la extrínseca busca sueldo, nota, aprobación o una consecuencia externa. Sin embargo, el autor considera demasiado simple dividir la vida en dos casillas. Comer bien para impresionar a otros y comer bien para mantener la energía son motivos técnicamente extrínsecos, pero el primero es controlado y el segundo puede ser autónomo, elegido porque importa a la persona. Su marco práctico pregunta de dónde sale la recompensa y si deja una sensación de alimento o de necesidad creciente. Lo conecta con el aprendizaje basado en recompensa y con la habituación: los elogios, el dinero y las métricas pueden exigir cada vez más, como el “fantasma hambriento” que nunca se sacia.

El ejemplo clásico de Deci con el rompecabezas Soma cube muestra el mecanismo. WebSockets vs. Long Polling vs. Server Sent Events📖 Texto completo

Anirban Singha12 de octubre de 20262 min read
WebSocketsSSElong pollingtiempo real

Anirban Singha compara tres formas sencillas de entregar actualizaciones en tiempo real y las explica desde la decisión de comunicación que necesita la interfaz. Con long polling, el navegador manda una petición y el servidor la mantiene abierta hasta que hay datos; cuando responde, el cliente vuelve a preguntar. Es una forma de evitar consultas cada pocos segundos, pero conserva el ciclo de peticiones y el artículo la reserva sobre todo para sistemas heredados. Server-Sent Events (SSE) abre un canal persistente en una sola dirección: el servidor puede enviar información cuando quiera y el navegador la recibe, pero el cliente no responde por el mismo canal. El texto usa como ejemplo el texto que aparece letra a letra en ChatGPT.

WebSockets son la opción para comunicación persistente y bidireccional. En lugar de abrir y cerrar solicitudes, establecen un túnel abierto en el que navegador y servidor pueden enviarse datos de forma inmediata. Esa característica los hace adecuados para casos en los que el usuario también necesita transmitir continuamente, como juegos o chats. SSE encaja mejor cuando la aplicación solo necesita que el servidor emita actualizaciones, por ejemplo en dashboards y notificaciones. Long polling sigue siendo una salida válida cuando la infraestructura existente impide adoptar un canal más moderno.

El criterio final del artículo es una sola pregunta: “¿el usuario necesita enviar datos de vuelta constantemente?”. Si la respuesta es sí, elegir WebSockets; si es no, SSE; si el sistema es antiguo o no permite otra cosa, long polling. Es un mapa de decisión introductorio, no una comparación de latencia, reconexión, escalabilidad, proxies, autenticación o costes de infraestructura. Su valor está en relacionar la dirección del flujo con el protocolo, evitando usar WebSockets por defecto cuando una transmisión unidireccional resolvería el problema o intentar SSE en una interacción que exige ida y vuelta.
